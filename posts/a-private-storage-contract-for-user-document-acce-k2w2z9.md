# A Private Storage Contract for User Document Access in Startup Apps

The operational constraint is simple: the storage service may move a user's bytes, but it must not decide who can see them. **Short answer: use a private file store behind application-owned document records, then issue a short-lived signed URL only after an access check.** That is the least complicated design that still has a clear answer when a user is removed from a workspace, a file is renamed, or a download link leaks into a support ticket.

The tempting version is an upload endpoint that accepts a browser filename, makes a public object, and saves its URL. It looks finished until the product needs tenant isolation, deletion, retries, previews, or a real audit trail. An S3-compatible alternative can make byte transport portable, but compatibility is not an authorization model. Keep the decision close to the app.

## How should a startup app handle private user-uploaded documents and signed URLs?

Give the same file three names, because they answer three different questions. A database record identifies the document in the product. An opaque object key identifies bytes in file storage. A display filename is what the user sees. Treating all three as one value is a small shortcut with a long tail: two people can upload `statement.pdf`, names can change, and raw filenames are not safe authority tokens.

The database row should carry the owning tenant, object key, original display name, content type, byte count, timestamps, and an explicit lifecycle state. The bucket or container stays private. When a user asks for a download, the application finds that row inside the current tenant, applies its ordinary authorization policy, and only then asks the storage layer for a time-limited grant. Possession of an object key should never be permission.

That separation also makes revocation legible. Removing a membership can stop future grants at the application boundary even though a previously minted URL remains usable until its expiry. Choose the expiry from the user action, not from a generic default: opening a small invoice may tolerate a brief grant, while a resumable upload needs a different path. Don't promise instant recall of a URL once it has been handed to a client; a signed URL is a bearer capability for its lifetime.

For user-visible downloads, set response metadata deliberately. HTTP `Content-Disposition` conveys whether content should render inline or download as an attachment, and it provides filename parameters for that presentation. The stored name remains untrusted input; pass it through a library or storage API that generates response metadata instead of concatenating a raw header string. MDN documents the relevant header behavior and encoding form.

Here is the boundary worth testing. It has no provider-specific types, so a test can run it against a local implementation and a remote S3-compatible service.

```ts
type DocumentRecord = {
  id: string;
  tenantId: string;
  objectKey: string;
  downloadName: string;
  mediaType: string;
  state: "pending" | "available" | "deleted";
};

type DownloadGrant = {
  url: URL;
  expiresAt: Date;
};

interface PrivateFileStore {
  createDownloadGrant(input: {
    objectKey: string;
    downloadName: string;
    mediaType: string;
    expiresInSeconds: number;
  }): Promise<DownloadGrant>;
}

async function grantDocumentDownload(
  document: DocumentRecord,
  tenantId: string,
  store: PrivateFileStore,
): Promise<DownloadGrant> {
  if (document.tenantId !== tenantId || document.state !== "available") {
    throw new Error("Document not found");
  }

  return store.createDownloadGrant({
    objectKey: document.objectKey,
    downloadName: document.downloadName,
    mediaType: document.mediaType,
    expiresInSeconds: 300,
  });
}
```

The important choice in that example is not the `300` value. It is that the handler receives a product record, not an object key supplied by the browser. A caller from another tenant gets the same application result as a caller asking for a missing record, which avoids turning the endpoint into an existence oracle.

## The simple upload path fails at completion, not at byte transfer

Uploading bytes is usually the easy part. Completion is where a startup app quietly creates orphaned files, duplicate processing, and documents that appear before their checks have finished.

Start with a pending record and an object key generated by the application. Allow the client to send only to that key. After the transfer, confirm that the expected object and metadata exist, then move the record to available. The confirmation operation must be safe to repeat, because clients retry and background work can be delivered more than once. Deletion wants the same treatment in reverse: remove the document from product access first, then run idempotent cleanup for the bytes.

The useful experiment is to trace one upload through every state, including an interrupted browser request and a repeated completion callback. Create the record before granting upload permission; bind the grant to the record's generated key; record completion without making the document visible; inspect the object; then publish the record once. A second completion for the same record should reach the same available state rather than create another document or trigger parsing again. A delete arriving during that sequence should leave the record unavailable to readers even if byte cleanup runs later. This ordering gives support and operations a plain vocabulary for every awkward case: pending means no user can download it yet, available means the verified object is reachable through policy, and deleted means the product no longer exposes it. The storage layer does not have to understand those meanings. The application does.

This is less glamorous than direct browser-to-storage upload. It is also where private access stays private. A direct upload grant should constrain the key, the allowed content type, and any size rule the product needs. A proxied upload through the application can be the better first deployment for tiny documents because validation and observability live in one request path. The catch is that the app then carries every byte, so request duration and memory behavior must be measured before calling it the default.

There is no universal breakpoint. File size distribution, upload abandonment, and the amount of post-upload processing decide it.

## What should the evaluation measure besides a signed-URL feature?

An S3-compatible API is a useful transport contract, not proof that the surrounding workflow meets the product's needs. Before selecting a service, run a small contract suite against the operations the app actually calls: write a representative object, read its bytes back, verify declared metadata, mint a download grant, check expiry behavior, and request deletion twice. Include names with spaces and non-ASCII characters, empty files, cancelled transfers, and duplicate completion messages.

Then inspect the whole route, including the parts that don't look like storage. A preview worker that reads an original repeatedly can multiply retrieval and downstream model-processing work. A parser retry can re-ingest the same document. A job that lacks an idempotency key can produce several records for one upload. Those are application behaviors, and storage billing follows application behavior rather than a bucket setting.

Keep a narrow evaluation sheet:

| Question | Evidence to collect |
| --- | --- |
| Can private access be enforced? | A cross-tenant request and an expired-grant test |
| Does the upload contract fit? | Object-size limits, metadata rules, and cancellation behavior |
| Can the app leave cleanly? | A record-to-object inventory and a verified export sample |
| What drives spend? | Stored bytes, reads, writes, downloads, and processing retries |
| Can the team operate it? | Logs without secrets, latency by workflow, and cleanup backlog |

Price pages often separate stored capacity, data transfer, and operation classes; the published categories are worth reading against a realistic workload rather than a single small PDF. The exact result depends on access frequency and retention, so no headline rate substitutes for a replay of an import spike and a reprocessing event. I'm not sure a startup needs elaborate forecasting in week one. It does need a way to notice when retries or previews change the request mix.

## Where private object storage is the wrong tool

Private object storage is a strong fit for immutable or mostly whole-object files such as PDFs, images, and archives, with searchable metadata kept in the application's database. It is not suitable when the central product action is querying or editing fields inside each document. Use a database or document-oriented model for data the product must filter and mutate as data, not as a blob.

There are other boundaries. Keep delivery behind the application when policy requires inspection on every download or an application-layer record of every byte served. Choose a document platform when collaborative editing, sharing semantics, and revision management are the product itself. Self-hosting can meet locality or control requirements, but it transfers backups, upgrades, capacity planning, and response work to the team. For a small team, that operational ownership may cost more attention than portability returns.

The decision should finish with an export rehearsal, not a checklist. List application records, map each to an object key, verify the selected sample's contents, identify records without objects and objects without records, and estimate how long the transfer would take. If that exercise is fuzzy, the storage choice isn't ready to copy.
